# Developer Notes


## Contributing

Contributions to `robodraw` are very welcome, whether they are bug reports,
documentation fixes, examples, tests, or new features. If you are planning a
larger change, opening an issue first is often the easiest way to check the
approach before spending too much time on implementation.

Please also read the
[`robodraw` Code of Conduct](https://github.com/jcmgray/robodraw/blob/main/CODE_OF_CONDUCT.md).

Things to check if new functionality is added:

1. Ensure functions are unit tested. `robodraw` is a single-module
   library — most code lives in `robodraw/schematic.py` — and tests
   **do not** compare rendered images. Assert instead on the matplotlib
   artists added to `d.ax` (e.g. `d.ax.patches`, `d.ax.lines`,
   `d.ax.texts`).
2. Reuse the `Drawing`'s own `_2d_project` / `_3d_project` helpers to
   compute expected positions, rather than hardcoding projected
   coordinates. This keeps the tests robust against changes to the
   projection math.
3. Tests that depend on `scipy` should use `pytest.importorskip("scipy")`
   — `scipy` is not in the `test` env, so a skip there is expected, not
   a failure.
4. Ensure functions have
   [NumPy-style docstrings](http://sphinxcontrib-napoleon.readthedocs.io/en/latest/example_numpy.html).
5. Ensure code is formatted and linted with `pixi run lint`.
6. The Sphinx API reference is generated by `sphinx-autoapi` from the
   docstrings in `robodraw/schematic.py`, so docstring quality is the
   API documentation. Keep public docstrings clear and complete.
7. Do not manually edit `robodraw/_version.py` — it is generated by
   `hatch-vcs` from git tags (a `0.0.0` version means no tags are
   reachable).
8. Add to changelog and elsewhere in docs.

## Development Setup

`robodraw` uses [pixi](https://pixi.sh) to manage development
environments and reproducible tasks. The environments and tasks are
defined in `pyproject.toml`, which is the source of truth for the
commands below. There are two environments: `test` (for running the
suite) and `docs` (for the lint/format/docs tasks).

After cloning the repository, install the pixi environments from the
project root:

```bash
git clone https://github.com/jcmgray/robodraw.git
cd robodraw
pixi install
```

You can then run project tasks with `pixi run ...`. For example, to run
a short Python command inside the test environment:

```bash
pixi run -e test python -c "import robodraw; print(robodraw.__version__)"
```


## Running the Tests

Testing `robodraw` is handled by pixi tasks in the `test` environment.
The most common commands are:

```bash
pixi run -e test test    # full suite with coverage, matches CI
```

The `test` task expands to:

```bash
pytest tests/ \
    --cov=robodraw \
    --cov-report=xml \
    --verbose \
    --durations=10
```

For a narrower check, use the `pytest` task (which also runs in the
`test` environment) and forward arguments after `--`:

```bash
pixi run -e test pytest tests/test_elements.py::test_element_smoke_adds_artist -q
```

`tests/conftest.py` forces the headless `Agg` matplotlib backend and
closes figures between tests, so a passing run is reproducible without
a display.

A smoke build of the sdist and wheel is also wired up:

```bash
pixi run -e test build-test
```


## Formatting the Code

`robodraw` uses [`ruff`](https://docs.astral.sh/ruff/) to format
imports and code style. The lint/format/docs tasks live in the `docs`
feature, so `pixi run` selects that environment automatically — do
*not* prefix them with `-e test`.

```bash
pixi run lint
pixi run format
```

The `format-all` task also runs notebook cleanup with `squeaky`:

```bash
pixi run format-all
```


## Building the docs locally

The documentation dependencies live in the `docs` pixi environment.
To build, clean, and serve the docs locally, use:

```bash
pixi run docs
pixi run docs-clean
pixi run docs-serve
```

The local server hosts the built docs at
`http://localhost:8000/`. The generated HTML is in
`docs/_build/html/`.

Notebooks under `docs/` and `docs/examples/` are rendered from stored
outputs by default (`nb_execution_mode = "off"`), not executed during
normal docs builds. Keep them runnable when refreshing those stored
outputs.

On ReadTheDocs, the build is driven by `.readthedocs.yml` and uses the
dedicated `readthedocs` pixi task.


## Minting a release

`robodraw` uses
[`hatch-vcs`](https://github.com/ofek/hatch-vcs) to derive the version
from git tags, and [GitHub Actions](https://github.com/jcmgray/robodraw/actions)
to publish to [PyPI](https://pypi.org/project/robodraw/). To mint a
new release:

1. Make sure all the
   [tests are passing on CI](https://github.com/jcmgray/robodraw/actions/workflows/tests.yml).
2. `git tag` the release with the next `vX.Y.Z`.
3. Push the tag to GitHub: `git push --tags`. The release workflow will
   build the sdist and wheel and upload them to the
   [PyPI **test** server](https://test.pypi.org/project/robodraw/).
4. If the test-pypi build looks good, create a GitHub release from the
   tag. Publishing the release triggers the same workflow to upload to
   the [PyPI **production** server](https://pypi.org/project/robodraw/).
5. The [`conda-forge/robodraw-feedstock`](https://github.com/conda-forge/robodraw-feedstock)
   repo should automatically pick up the new PyPI release and build a
   new [conda package](https://anaconda.org/conda-forge/robodraw); the
   recipe should only need to be manually updated if there are, for
   example, new dependencies.

Alternate manual release steps (after tagging):

1. Remove any old builds: `rm -rf dist/*`
2. Build the sdist and wheel: `python -m build`
3. Upload using twine: `twine upload dist/*`
